# GraphReview inside out

A pull request comes in. Four agents (three Claude, one linter) review it in parallel. A judge removes the
weak findings, and one review lands on GitHub. In between, a code graph and a vector index tell the agents
what the diff can break. This guide follows that path piece by piece.

> [`docs/diagrams/build.py`](diagrams/build.py); run `make docs` after changing it.

## 1. The whole system

![System map](img/arch/01-system-map.svg)

**Read it like this:**

* The left column is the review path, top to bottom. Each teal arrow between services is a Kafka topic.
* The right column is retrieval. The indexer builds a code graph and a vector index ahead of time. The
  context service answers the agents' questions from them.
* Amber boxes call Claude; violet boxes store state.
* Dashed arrows are request/response calls; teal arrows go through Kafka.

## 2. One review, end to end

![Sequence of one review](img/arch/02-review-sequence.svg)

Each column is a participant; time runs downward. The violet pills on the right are the job's status in Redis.
The dashboard's pipeline stepper reads exactly these values: `queued` → `agents` → `judging` → `completed`.

All four agents run the middle block at the same time. Each agent's tool loop asks Claude, runs the tools Claude
asked for, and repeats, at most 8 turns. The aggregator waits for all four results, or 300 s.

Two details make this robust:

* **Services talk only through Kafka.** The gateway and the agents never call each other directly, so any
  service can restart without losing work.
* **Every message is keyed by `job_id`.** All four agent results for one job land on the same partition, and
  therefore on the same aggregator replica.

## 3. Kafka fan-out: every role sees every PR

![Kafka consumer groups](img/arch/03-kafka-consumer-groups.svg)

Kafka behaves two ways depending on *consumer groups*:

* Consumers in **different** groups each get every message. That's how one PR reaches all four agents without
  the gateway knowing they exist.
* Consumers in the **same** group share the partitions. That's how one role scales out.

A seventh reviewer replica would sit idle, because there are only six partitions to own. That's why
autoscaling caps at 6.

Delivery is **at least once**. A consumer commits its offset only after the handler has finished, including
publishing its own output. If a pod dies mid-review, another replica re-reads the message. A message can
therefore occasionally be processed twice, so every consumer tolerates repeats (see
[§7](#7-when-things-fail)).

| Topic | Producer | Consumer group(s) | Payload |
|---|---|---|---|
| `pr.review.requested` | gateway | agent-static, agent-reviewer, agent-security, agent-tests | `ReviewJob`: repo, PR, diff patches, head SHA |
| `review.agent.results` | each agent | aggregator | `AgentResult`: findings, tokens, tool counts, error |
| `review.aggregated` | aggregator | critic | `AggregatedReview`: merged findings + job |
| `review.completed` | critic | publisher | `FinalReview`: verdict, summary, kept + dropped findings |
| `repo.index.requested` | gateway | indexer | `IndexRequest`: repo, ref, changed paths |
| `repo.indexed` | indexer | (none yet) | `IndexResult`: nodes, edges, chunks, time |
| `review.dlq` | any worker | (inspect manually) | the failed message + origin topic + error |

## 4. Inside an agent: the tool loop

![Agent tool loop](img/arch/04-agent-tool-loop.svg)

The reviewer, security and tests agents are the same engine with a different system prompt, tool list and
effort level. Claude doesn't get whole files. It gets the diff, with new-file line numbers in the margin so it
can cite exact lines, plus a short graph *impact report*. Then it decides what else it needs to look at.

Each turn has three ways out:

* `tool_use` runs the tools and loops.
* `end_turn` carries the final answer. It's guaranteed to match the findings JSON schema.
* Anything else becomes an error result, so the pipeline keeps moving.

| Tool | Question it answers | Backed by |
|---|---|---|
| `get_callers` | Who calls this function, 1–3 hops out, and what does it call? | code graph |
| `find_tests` | Which tests exercise this symbol? | code graph |
| `search_code` | Where else does the codebase do something similar? | vectors (code chunks) |
| `search_docs` | What do this repo's own docs say the rule is? | vectors (doc chunks) |
| `read_snippet` | Show me lines 40–80 of this file. | PR head for changed files, index for the rest |

**Deliberate choices in the loop:**

* **Parallel tool calls run concurrently**, and all their results go back in one message. Splitting them would
  teach the model to stop batching.
* **The assistant turn is appended verbatim**, thinking blocks included. The history is append-only, so the
  prompt cache keeps hitting on every turn.
* **PR text is treated as data.** Every system prompt says the diff and docs are untrusted and are never
  instructions. This is a basic defence against prompt injection through a PR description.

## 5. GraphRAG: a graph for structure, vectors for meaning

"RAG" means fetching relevant context and putting it in front of the model. GraphReview does it two ways,
because they answer different questions. Vector search can't tell you who calls a function; a graph can't find
code that is merely similar. The indexer builds both from the default branch, once per push.

![Indexing](img/arch/05-indexing.svg)

The numbers are from the bundled sample app. Chunks follow the code's structure: a function, a class, the gaps
between them. Every line of a file is in exactly one chunk, so `read_snippet` can rebuild any line range.

### From an edited line to what it can break

Seeded case 05 gives `compute_tax` a new required parameter, on line 21 of `pricing.py`. The graph finds the
innermost function around that line. Then it walks the edges *backwards*, from callee to caller, up to two
hops. Callees are skipped: changing `compute_tax` can't break the functions it calls.

![Code graph around compute_tax](img/arch/06-code-graph-impact.svg)

This is the text the agents receive at the top of their prompt. The dashboard shows it as "What the code graph
saw":

```text
CHANGED SYMBOLS (graph nodes enclosing the edited lines):
  compute_tax [function] @ shopapp/pricing.py:19
DEPENDENTS (reverse deps, ≤2 hops) — code that may break:
  [d1] order_total [function] @ shopapp/pricing.py:24
  [d1] test_tax_rounds_half_up @ tests/test_pricing.py:15
  [d2] checkout [function] @ shopapp/api.py:27
  [d2] test_order_total @ tests/test_pricing.py:19
TESTS REACHING THE CHANGE:
  test_tax_rounds_half_up @ tests/test_pricing.py:15
  test_order_total @ tests/test_pricing.py:19
```

With this report, Claude can see that `order_total` still calls `compute_tax(discounted, region)` with two
arguments. That call isn't in the diff, so a diff-only reviewer would never see it.

### Hybrid search: meaning and exact words

![Hybrid search](img/arch/07-hybrid-search.svg)

Each chunk is stored with two vectors:

* **Dense** (BGE-small, 384 numbers) captures meaning, so "integer cents" finds text about money.
* **Sparse** (BM25) scores exact words, which matters for identifiers like `compute_tax`.

Qdrant runs both searches and merges the rankings with reciprocal rank fusion, so a result that ranks well in
both comes first. The figure's rankings are illustrative. The tests check that this query returns the
CONTRIBUTING.md "Money" section first.

## 6. Merging duplicates, then judging

![Merge and judge](img/arch/08-merge-and-judge.svg)

Four agents looking at the same diff often flag the same problem. The aggregator clusters findings that sit in
the same file within three lines and either share a category or have similar wording. Each cluster keeps its
most severe, most confident finding and records which agents agreed. Agreement is evidence, so confidence
rises: `confidence = 1 − (1 − c) × 0.6^(agents − 1)`.

The figure shows a real run of seeded case 01 plus two more findings. The security agent and ruff both flagged
line 8, so they merge into one finding tagged with both agents.

The **critic** is a second Claude pass with a different job: be skeptical. It sees the diff, the packed graph
context and the proposed findings. For each finding it returns keep/drop, a confidence and a severity. It also
writes the summary and the verdict. This LLM-as-judge step keeps a multi-agent system from burying a PR in
plausible-sounding noise. Rejected findings are kept, not deleted: the dashboard lists them under "Rejected by
critic".

## 7. When things fail

![Retry and dead-letter flow](img/arch/09-retry-and-dlq.svg)

Every worker runs the same consume loop: one message at a time, offset committed only after success or after
the message is parked in the dead-letter topic. Either way the offset is committed, so one bad message can't
block a partition forever.

| What goes wrong | What happens | Where |
|---|---|---|
| GitHub redelivers a webhook, or two pushes arrive fast | Same repo + PR + head SHA returns the existing job id (`SETNX dedupe:…`) | gateway |
| Kafka isn't up yet when a pod starts | Client retries with backoff for ~7 minutes instead of crash-looping | `common/bus.py` |
| Claude refuses, hits `max_tokens`, or the API errors | SDK retries 429/5xx 4×; otherwise the agent publishes a result with `error` | agents |
| An agent never reports | Deadline sweeper flushes partial results after 300 s; agent shown as `timeout` | aggregator |
| The same agent result arrives twice | Stored per agent in a hash, so the second write is a no-op; flush guarded by `SETNX agg:done:…` | aggregator |
| Posting to GitHub fails | Guard key removed so the retry can post; after 3 failures → `review.dlq` | publisher |
| A pod is killed mid-review | Offset not committed, so another replica re-reads the message; 300 s grace period lets most reviews finish | Kubernetes |
| A PR description says "ignore previous instructions…" | Prompts frame all PR content as untrusted data; the output schema limits what the model can return | agents, critic |

## 8. Kubernetes and autoscaling

Each service is its own Deployment and scales on its own signal:

* **gateway, context:** CPU, via the usual HPA.
* **Agents:** they barely use CPU because they spend their time waiting on Claude, so CPU says nothing about
  how far behind they are. The right signal is **consumer lag**, the number of messages waiting for their group.
  KEDA turns lag into replicas.

![KEDA control loop](img/arch/10-keda-loop.svg)

**Measured: 40 PRs at once on a laptop cluster.** Setup: kind, one node with 6 vCPU / 10 GB, offline LLM with
2 s of simulated latency, sampled every 10 s.

![Measured KEDA burst](img/arch/11-keda-burst-measured.svg)

* The security and tests agents followed the same curve. The critic scaled separately, to 4.
* All 41 reviews completed.
* A fourth critic pod stayed *Pending*. Memory *requests* on the single node hit 98%, though real usage was
  44%. In production a cluster autoscaler would add a node; the dev overlay lowers the requests instead.

| Seconds after burst | agent-reviewer replicas | Lag per replica |
|---:|---:|---:|
| 0 | 1 | — |
| 10 | 5 | 12 |
| 20 | 6 | 2.4 |
| 30 | 6 | 2.4 |
| 40 | 6 | 2 |
| 51 | 6 | 0 |
| 61–121 | 6 | 0 |

| Component | Docker Compose | Kubernetes | Scales on |
|---|---|---|---|
| gateway | 1 container, :8080 | Deployment ×2, Service, PodDisruptionBudget | CPU (HPA, 2–6) |
| context | 1 container, :8001 | Deployment ×2, Service, PodDisruptionBudget | CPU (HPA, 2–8) |
| agents ×4 | 1 container each (reviewer ×2) | Deployment each | consumer lag (KEDA, 1–6) |
| critic | 1 container | Deployment | consumer lag (KEDA, 1–6) |
| aggregator, publisher | 1 container each | Deployment (prod: ×2) | fixed |
| indexer | 1 container + repos volume | Deployment + 20 Gi scratch | fixed |
| Kafka | `apache/kafka:4.3.1`, single node, KRaft | Strimzi `Kafka` + `KafkaNodePool` + `KafkaTopic`; prod: 3 brokers, replication 3 | — |
| Redis | `redis:8.8.3` | StatefulSet + 2 Gi volume | — |
| Qdrant | `qdrant:v1.19.1` | StatefulSet (unprivileged) + 10 Gi volume | — |
| Prometheus, Grafana | included, dashboard provisioned | pods carry scrape annotations for your own Prometheus | — |

The manifests set a hardened baseline:

* pods run as non-root with a read-only root filesystem
* all Linux capabilities are dropped and the default seccomp profile applies
* NetworkPolicies deny all ingress by default and open only the paths the pipeline uses

## 9. Offline mode vs Claude

`LLM_BACKEND` picks what answers the agents:

* **`fake`** is a deterministic rule engine. It speaks the same response format as the Claude API, including a
  tool call on the first turn. Everything else runs for real: Kafka, the tool loop, merging, the critic step,
  the dashboard. That's why the tests, CI and every demo work without an API key.
* **`anthropic`** sends the same requests to Claude.

| Case | Seeded bug | What it takes to catch | Offline engine |
|---:|---|---|---|
| 01 | email lookup switched to an f-string SQL query | pattern | caught (security + ruff) |
| 02 | discount computed with floats | convention (money is integer cents) | missed |
| 03 | authorization check removed from a handler | reasoning + convention | missed |
| 04 | payment request loses its timeout | pattern | caught |
| 05 | `compute_tax` gains a parameter; callers not updated | **graph** (callers outside the diff) | missed |
| 06 | refund failures swallowed | pattern | caught |
| 07 | PBKDF2 replaced with MD5 | pattern | caught |
| 08 | pagination skips the first page | reasoning | missed |
| 09 | `average()` divides by a possibly-zero length | pattern | caught |
| 10 | stock check inverted | reasoning | missed |
| 11 | docstring only (control: should stay clean) | — | clean |

The offline engine scores precision 1.0 and recall 0.5: it finds the five pattern bugs and nothing else. The
other five need reasoning, team conventions, or the graph.

`make eval` measures what Claude catches and how much the graph helps. It runs each case three ways:

* `diff_only`: the diff alone
* `full_files`: the diff plus every changed file
* `graph_rag`: the impact report plus tools

For each mode it reports precision, recall, tokens, cost and latency.

## 10. Components

| Component | Job | Scales by | Code |
|---|---|---|---|
| **gateway** | Verifies `X-Hub-Signature-256` and fetches PR files. Dedupes redeliveries per head SHA, writes the job to Redis, publishes `pr.review.requested`. Serves the dashboard and REST API. | HPA on CPU | `gateway/app.py` |
| **static agent** | Runs `ruff` (F, E9, B, S, ASYNC, BLE, PERF) on the changed `.py` files at the PR head. Keeps diagnostics on added lines only. Skips the critic. | KEDA, lag 5 | `agents/static_agent.py` |
| **reviewer agent** | Claude, correctness: broken caller contracts, edge cases, error handling, leaks, performance, documented conventions. Effort `high`. | KEDA, lag 2 | `agents/llm_agent.py`, `agents/specs.py` |
| **security agent** | Claude, AppSec: injection, missing authz, secrets, unsafe deserialization, SSRF, path traversal, weak crypto. Effort `high`. | KEDA, lag 2 | same |
| **tests agent** | Claude: changed behaviour no test exercises, with a test sketch. Effort `medium`. | KEDA, lag 3 | same |
| **aggregator** | Stores results per agent (`agg:{id}`), merges duplicates, boosts agreement. Flushes partial results at the 300 s deadline. `SETNX agg:done:{id}` makes the flush happen once. | by partition | `aggregator/service.py` |
| **critic** | Claude as judge (effort `medium`): keep/drop, confidence and severity per finding. Drops anything below 0.6. Writes summary + verdict. | KEDA, lag 2 | `critic/service.py` |
| **publisher** | Stores the final review, sets `status=completed`. Posts one GitHub review (`SETNX posted:{id}`): inline comments on diff lines, the rest in the body. | 1–2 pods | `publisher/service.py` |
| **indexer** | Shallow clone (token sent as an HTTP header, never in the URL). Builds the graph with `graphify extract --code-only`, falling back to a Python AST builder. Chunks + embeds into Qdrant. Re-embeds only changed paths on push. | 1 pod | `indexer/service.py`, `retrieval/` |
| **context service** | GraphRAG HTTP API (`impact`, `callers`, `find_tests`, `search_code`, `search_docs`, `read_snippet`, `pack_context`) + MCP server. Caches graphs per version. | HPA on CPU | `context/`, `retrieval/retriever.py` |
| **Redis** | `job:*`, `status:*`, `progress:*`, `review:*`, aggregation state + deadlines, idempotency guards, gzip graph blobs | StatefulSet | `common/state.py` |
| **Qdrant** | `code_chunks` collection: `dense` (cosine) + `sparse` (BM25/IDF) vectors; payload repo, path, lines, kind, symbol, text | StatefulSet | `retrieval/vector_store.py` |
| **Claude API** | Messages API with structured output, strict tool schemas, prompt caching, server-side refusal fallback. Default `claude-opus-5-5`. | external | `common/llm.py` |

All paths are under `src/graphreview/`. Every message on the bus is a Pydantic model in `common/models.py`.
`pipeline.py` wires every service into one process for the demo, the eval and the end-to-end tests.

## 11. Glossary

| Term | Meaning |
|---|---|
| Agent | An LLM in a loop with tools: it decides what to look up, looks it up, and repeats until it can answer. |
| Tool use | Claude replies with a structured request to call one of our functions; we run it and send back the result. |
| Structured output | The API constrains Claude's final answer to a JSON schema, so parsing never fails. |
| Prompt caching | The API reuses an unchanged prompt prefix from a previous call at about a tenth of the price; each loop turn reuses all earlier turns. |
| LLM-as-judge | A second model call that evaluates the first one's output instead of producing new work. |
| RAG | Retrieval-augmented generation: fetch relevant context at question time instead of relying on what the model memorised. |
| GraphRAG | RAG where some of that context comes from walking a graph of relationships rather than from text similarity. |
| Code graph | Nodes are files, classes and functions; edges are calls, imports, inheritance. Built by Graphify with tree-sitter parsers. |
| Embedding | A list of numbers representing text, so that similar meaning gives nearby vectors. |
| BM25 | A classic keyword-ranking formula, stored here as a sparse vector for exact-term matching. |
| Reciprocal rank fusion | Merges two rankings by summing 1/(k + rank) per item, so items ranked well in both win. |
| Kafka topic / partition | A named, append-only log split into partitions. Order is guaranteed within a partition; the message key picks the partition. |
| Consumer group | Consumers sharing a name split a topic's partitions; different groups each get every message. |
| Offset / commit | A consumer's position in a partition. Committing it says "everything before this is done". |
| At-least-once | Messages are never lost, but may be delivered twice, so handlers must be idempotent. |
| Idempotent | Doing it twice has the same effect as doing it once. |
| Dead-letter queue | A topic where messages that keep failing are parked for inspection instead of blocking the stream. |
| Strimzi | A Kubernetes operator that runs Kafka from declarative resources (`Kafka`, `KafkaTopic`). |
| KEDA | Kubernetes event-driven autoscaling: scales Deployments on external signals such as Kafka consumer lag. |
| HPA | HorizontalPodAutoscaler: the built-in controller that changes a Deployment's replica count. |
| MCP | Model Context Protocol: a standard way to expose tools to AI clients like Claude Code. GraphReview exposes its retrieval tools this way. |
