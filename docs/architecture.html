Field guide · graphreview 0.2.0

GraphReview Inside Out

A pull request comes in, four AI and lint agents review it in parallel, a judge throws out the weak findings, and one review lands on GitHub. In between, a code graph and a vector index tell the agents what the diff can break. This page follows that path piece by piece.

  • 4 agents
  • 7 Kafka topics
  • 5 agent tools
  • 2 stores (Redis, Qdrant)
  • 11 seeded-bug test PRs

The whole system

The left column is the review path, top to bottom: each arrow between services is a Kafka topic. Front door: webhooks, REST API and the dashboard.

aggregator

Joins the four results for a job and merges duplicates.

  • Stores each result in Redis hash agg:{id} (one field per agent, so redelivery is harmless) and per-agent progress for the dashboard.
  • When all expected agents reported: cluster findings (same file, ±3 lines, same category or similar text), boost confidence when agents agree, publish review.aggregated.
  • A sweeper flushes partial results after 300 s and marks missing agents timeout.
  • SETNX agg:done:{id} makes the flush happen once across replicas.

Builds the two indexes the agents search.

Claude API

The model behind the reviewer, security, tests and critic agents.

Sequence

One review, end to end

Each column is a participant; time runs downward. Teal arrows travel through Kafka, dashed ones are replies, violet ones write to Redis. The violet pills on the right are the job's status. The dashboard's pipeline stepper reads exactly these four values:

  • queued→
  • agents→
  • judging→
  • completed

Two details make this robust. The gateway and the agents never talk to each other directly: everything goes through Kafka, so any service can restart without losing work. And every Kafka message for a job is keyed by its job_id, so all four agent results for one job land on the same partition and therefore the same aggregator replica.

Messaging

Kafka fan-out: every role sees every PR

Kafka gives two behaviours depending on consumer groups. Consumers in different groups each get every message, which is how one PR reaches all four agents without the gateway knowing they exist. Consumers in the same group share the partitions, which is how one role scales out.

Delivery is at least once: a consumer commits its offset only after the handler has finished, including publishing its own output. If a pod dies mid-review, another replica picks the message up again. That means a message can occasionally be processed twice, so every consumer is written to tolerate repeats (see When things fail).

Agents

Inside an agent: the tool loop

The reviewer, security and tests agents are the same engine with a different system prompt, tool list and effort level. Claude doesn't get whole files. It gets the diff (with new-file line numbers in the margin, so it can cite exact lines) and a short graph impact report, then decides what else it needs to look at.

ToolQuestion it answersBacked by
get_callersWho calls this function, 1–3 hops out, and what does it call?code graph
find_testsWhich tests exercise this symbol?code graph
search_codeWhere else does the codebase do something similar?vectors code chunks
search_docsWhat do this repo's own docs say the rule is?vectors doc chunks
read_snippetShow me lines 40–80 of this file.PR head for changed files, index for the rest

A few deliberate choices in the loop:

  • Parallel tool calls run concurrently and all their results go back in one message. Splitting them would teach the model to stop batching.
  • The assistant turn is appended verbatim, including thinking blocks, so the history is append-only and the prompt cache keeps hitting on every turn.
  • The PR's text is treated as data. Every system prompt says the diff and docs are untrusted and are never instructions. That's a basic defence against prompt injection in a PR description.

Retrieval

GraphRAG: a graph for structure, vectors for meaning

"RAG" means fetching relevant context and putting it in front of the model. GraphReview does it two ways, because they answer different questions. A vector search can't tell you who calls a function; a graph can't find code that is merely similar. The indexer builds both from the default branch, once per push.

Reading the graph: from an edited line to what it can break

Take seeded case 05, where compute_tax gains a required parameter. The edited line is 21 of pricing.py. The graph finds the innermost function around that line, then walks the edges backwards (from callee to caller) up to two hops. Callees are skipped: changing compute_tax can't break the functions it calls.

CHANGED SYMBOLS (graph nodes enclosing the edited lines):
  compute_tax [function] @ shopapp/pricing.py:19
DEPENDENTS (reverse deps, ≤2 hops) — code that may break:
  [d1] order_total [function] @ shopapp/pricing.py:24
  [d1] test_tax_rounds_half_up @ tests/test_pricing.py:15
  [d2] checkout [function] @ shopapp/api.py:27
  [d2] test_order_total @ tests/test_pricing.py:19
TESTS REACHING THE CHANGE:
  test_tax_rounds_half_up @ tests/test_pricing.py:15
  test_order_total @ tests/test_pricing.py:19

The right panel is the actual text the agents receive at the top of their prompt (it's also the "What the code graph saw" card on the dashboard). With it, Claude can see that order_total still calls compute_tax(discounted, region) with two arguments. That file isn't in the diff, so a diff-only reviewer would never look at it.

Hybrid search: meaning and exact words

For "how does this repo handle X" questions, each chunk is stored with two vectors. The dense one (BGE-small, 384 numbers) captures meaning, so "integer cents" finds text about money. The sparse one (BM25) scores exact words, which matters for identifiers like compute_tax. Qdrant runs both searches and merges the rankings with reciprocal rank fusion.

Aggregation

Merging duplicates, then judging

Four agents looking at the same diff often flag the same problem. The aggregator clusters findings that sit in the same file within three lines and share a category, or have similar wording. Each cluster keeps its most severe, most confident finding and records which agents agreed. Agreement is evidence, so confidence rises:

confidence = 1 − (1 − c) × 0.6^(agents − 1)

The critic is a second Claude pass with a different job: be skeptical. It sees the diff, the packed graph context and the proposed findings, and returns a keep/drop decision, a confidence and a severity for each one, plus the summary and verdict. This "LLM-as-judge" step is what keeps a multi-agent system from burying a PR in plausible-sounding noise. Rejected findings aren't deleted; the dashboard lists them under "Rejected by critic".

Reliability

When things fail

Every worker runs the same consume loop. A message is processed one at a time per consumer, and its offset is committed only after the handler succeeds or the message has been parked in the dead-letter topic.

Deployment

Kubernetes and autoscaling

Each service is its own Deployment, so each one scales on its own signal. The HTTP services (gateway, context) scale on CPU, the standard way. The agents don't use much CPU, though: they spend most of their time waiting on Claude. So CPU says nothing about how far behind they are. The right signal is consumer lag, the number of messages waiting in their group, and KEDA turns that into replicas.

Measured: 40 PRs at once on a laptop cluster

One more thing that run showed: a fourth critic pod stayed Pending because the single node's memory requests hit 98%, though real usage was 44%. That's the scheduler working as designed. In production a cluster autoscaler would add a node; on a laptop, the dev overlay lowers the requests.

Two brains

Offline mode vs Claude

LLM_BACKEND picks what answers the agents. fake is a deterministic rule engine that speaks the same response format as the Claude API, including a tool call on the first turn. Everything else (Kafka, the tool loop, merging, the critic step, the dashboard) runs for real. That's why the tests, CI and every demo work without an API key. anthropic sends the same requests to Claude.

The offline engine scores precision 1.0 and recall 0.5: it finds the five pattern bugs and nothing else. The other five need reasoning, team conventions, or the graph. Measuring how Claude does on them, and how much the graph context helps compared with sending only the diff or whole files, is what make eval is for. That's the next step, and it needs an API key.

The eval runs each case three ways: diff_only (the diff alone), full_files (the diff plus every changed file), and graph_rag (impact report plus tools). It reports precision, recall, tokens, cost and latency for each. That ablation is what shows the graph pays for itself.

Terms

Glossary

Agent
An LLM in a loop with tools: it decides what to look up, looks it up, and repeats until it can answer.
Tool use
Claude replies with a structured request to call one of our functions; we run it and send back the result.
Structured output
The API constrains Claude's final answer to a JSON schema, so parsing never fails.
Prompt caching
Claude's API reuses an unchanged prompt prefix from a previous call at about a tenth of the price; each loop turn reuses all earlier turns.
LLM-as-judge
A second model call that evaluates the first one's output instead of producing new work.
RAG
Retrieval-augmented generation: fetch relevant context at question time instead of relying on what the model memorised.
GraphRAG
RAG where some of that context comes from walking a graph of relationships rather than from text similarity.
Code graph
Nodes are files, classes and functions; edges are calls, imports, inheritance. Built by Graphify with tree-sitter parsers.
Embedding
A list of numbers representing text, so that similar meaning gives nearby vectors.
BM25
A classic keyword-ranking formula; here it's stored as a sparse vector for exact-term matching.
Reciprocal rank fusion
Merges two rankings by summing 1/(k + rank) for each item, so items ranked well in both win.
Kafka topic / partition
A named, append-only log split into partitions. Order is guaranteed within a partition; the message key picks the partition.
Consumer group
Consumers sharing a name split a topic's partitions; different groups each get every message.
Offset / commit
A consumer's position in a partition. Committing it says "everything before this is done".
At-least-once
Messages are never lost, but may be delivered twice, so handlers must be idempotent.
Idempotent
Doing it twice has the same effect as doing it once.
Dead-letter queue
A topic where messages that keep failing are parked for inspection instead of blocking the stream.
Strimzi
A Kubernetes operator that runs Kafka from declarative resources (Kafka, KafkaTopic).
KEDA
Kubernetes event-driven autoscaling: scales Deployments on external signals such as Kafka consumer lag.
HPA
HorizontalPodAutoscaler: the built-in Kubernetes controller that changes a Deployment's replica count.
MCP
Model Context Protocol: a standard way to expose tools to AI clients like Claude Code. GraphReview exposes its retrieval tools this way.
